# Staff customers, reservations and orders

The existing staff routes `/admin/customers`, `/admin/reservations` and `/admin/orders` now provide operational tables and detail views. Admin and SuperAdmin share these workflows. They use the generated feature services through the sole Axios boundary in `src/API.tsx`. The operational route module remains lazy and is loaded only after the staff guard succeeds. No backend source, schema, runtime dependency or authentication behavior is changed.

Customer lists use only `pageNumber`, `pageSize`, `search` and `isDeleted`. Search matches the backend's names/email behavior, is limited to 100 characters and debounced by 300 ms. Its text stays in route-local memory and is excluded from SPA URLs/history and persistent storage. Paging/filter URLs are canonical, with a page-size maximum of 100. The page also removes unsupported parameters and returns an out-of-range page to the current last page. Failed reads keep filter controls and their values available. Tables have a labeled, keyboard-focusable horizontal scrolling region; reference/phone values retain their direction and intact codes on mobile.

Customer DTOs expose first/last name, email, phone and deletedAt. They omit the identity number and do not support staff registration/profile editing. Soft deletion sets the backend's deleted timestamp; it is not physical erasure. Deleted customers remain readable through the detail endpoint. Restoration can fail on account-detail collisions. The UI confirms both actions and re-reads the target customer plus the affected current list where applicable. Separate deletion/restoration state shares a synchronous write gate to prevent conflicting actions.

Reservation and order lists use separate staff endpoints and only paging/status parameters. There is no invented date filter, customer join, reservation-number search endpoint or `/me` query. Reservation details show the server status and linked order ID. Conversion is offered only for Processing reservations with no linked order. The bodyless `POST /api/v1/admin/reservations/{reservationId}/order` sends neither a price nor a fabricated empty body. The frontend reads the reservation and the returned order GUID, verifies their relationship, and displays the server's total/status through the linked order. The backend atomically confirms the reservation and creates either an initiative Pending order or a regular Processing order.

Completion uses the bodyless `POST /api/v1/admin/orders/{id}/complete`. The handler requires a Pending initiative order and refuses an existing winner. Accepting a selection completes that order, records the server timestamp and cancels the other orders for the same unit. The confirmation explains this consequence. The DTO does not include project type; Pending-only button visibility follows the current creation invariant, rather than inventing a project-type field or joining all inventory. The handler still determines eligibility, including legacy/inconsistent records or concurrent changes. The operation re-reads current order status and invalidates any other mounted order views. Conversion/completion also invalidate mounted public catalogue views whose unit availability may change.

Reservation/order DTOs expose their mutual IDs and unit ID, but omit customerId and projectId. Only supported reservation/order cross-links are rendered. Project/unit names and codes remain supplied content. A unit link cannot be built without its required project ID, and missing customer relationships are not reconstructed by downloading customer lists. No payments, exports, revenue calculations or KPI endpoints are introduced.

`CustomerOperationsProvider`, `ReservationsAdminProvider` and `OrdersAdminProvider` are focused route-local contexts keyed by staff actor, profile ID, generation and pathname. `useStaffRead` supplies awaitable cancellation-aware reads with latest-response/generation protection; loading/error states discard the prior DTO. Its stable reload handle resolves the latest query, so an outcome check retained by an earlier action cannot restore an obsolete filter. The original action's target ID remains fixed. `useStaffOperation` gives each operation its own pending, failure, success and uncertainty state. Related operations share a synchronous gate, and the lock covers both the write and authoritative follow-up reads. StrictMode setup replay does not dispatch a duplicate initial read.

Definitive 403/404/409 responses reconcile current state without replaying the mutation. 429 remains a safe localized rejection with transport Retry-After metadata and no automatic retry. Interrupted/network/5xx/malformed-success results, or failures after an acknowledged write, block another operation until an explicit current-outcome check succeeds. A known returned order GUID is retained in memory for follow-up reads. If no GUID was acknowledged, reconciliation checks the reservation and its current linked order. Canceling navigation/request transport does not imply server rollback. Confirmations protect pending actions; route unmount/logout aborts requests, rejects late actor-generation results and discards private state.

Only locale/session coordination hints use existing persistence. Operational DTOs, selected customer data, filter search text and outcomes are not persisted or logged. Browser evidence uses synthetic inventory and masks customer names, email, phone and search controls before saving screenshots. Real API/SQL/account-policy/cookie verification still needs the configured backend and dedicated verification accounts recorded in the inherited [session dependency](session-verification.md).
